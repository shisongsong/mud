# 即时合作动作 RPG 产品与战斗设计 v1.0

- 状态：首发产品方向定稿；系统数值是待验证的设计基线，不代表平衡或留存已验证。
- 日期：2026-10-10。
- 变更原因：替代旧 M0 将“阅读线索→投票→结算”当作核心玩法、并把职业限定为展示身份的产品假设。
- 范围：浏览器端四人合作、实时 PvE、角色构筑、战役任务与持续世界；不复制任何特定游戏的世界观、角色、技能、物品、文案、地图或美术表达。

## 1. 产品承诺

玩家和最多三位伙伴组成小队，选择角色构筑，进入有叙事目标的任务；在探索中发现威胁与线索，以即时战斗和团队协作克服遭遇，带着经验、装备和世界后果返回据点，再决定下一步战役行动。

游戏的差异不应只是“线上玩一个剧本”，也不应只是“把刷怪数值套上剧情”。叙事决定任务目标和局势，构筑改变玩家处理威胁的方式，战斗与任务结果改变后续战役状态。玩家需要在一场中感受到操作/合作，在数场之间感受到成长和后果。

《暗黑破坏神》等动作 RPG 仅作高层系统参考：即时定位与技能循环、装备驱动的流派选择、清楚的战利品反馈。调查叙事可参考技能改变角色观察/对话方式的 RPG 设计。借鉴设计问题，不复用其表达或具体内容。

## 2. 首发形态

- 平台：浏览器桌面端优先；固定斜俯视 2D/2.5D 战场，键盘移动与鼠标瞄准/交互。控制器和移动端待可用性验证，不作为首发门槛。
- 队伍：1–4 人合作 PvE；敌人生命、数量和机制按队伍规模调整。单人也能完成主线，不强制职业或玩家数量检查。
- 单次任务目标：约 15–25 分钟，包含据点配装、探索/目标推进、至少两类战斗遭遇和一次精英或首领战、结算与成长选择。
- 首发非目标：PvP、公会/大型团本、玩家交易、无限赛季、抽卡、真实货币战力、玩家编程规则。未有玩法证据前不建设无限内容运营系统。
- 四职业、有限地图和可控战利品是首发内容规模，不限制后续添加职业、技能、敌人、装备定义或章节。

## 3. 核心循环

1. **据点准备**：领取战役任务、查看公开情报、选择职业构筑、整理装备和快捷道具。
2. **进入任务**：小队进入同一任务版本，完成移动、交互和可选目标；环境线索用于理解威胁、寻找路线或取得战斗优势。
3. **实时遭遇**：识别敌人意图，移动/闪避/打断/控制/输出；团队可以组合技能，但每个角色均有基本自保和贡献能力。
4. **战役结果**：首领/任务完成、失败或撤退都写入明确结果；失败不应无条件清空全部成长或卡死主线。
5. **成长反馈**：获取经验、装备和任务资源；比较物品、强化或更换技能/天赋，形成可理解的构筑变化。
6. **世界推进**：关键任务结果改变有限且可见的世界状态，解锁后续任务、盟友/敌人状态或场景变化，而不只改面板数字。

叙事和探索不另做一套与战斗无关的投票小游戏。对话、调查、环境互动和任务选择应能改变遭遇条件、可选目标、奖励或后续状态；战斗是主循环，不是最后附加的迷你模式。

## 4. 实时战斗

### 4.1 操作基线

- WASD 移动，鼠标指向/选取目标；左键基础攻击，右键闪避，Q/E/R/F 装备四个主动技能，Space 交互/确认。键位可重映射。
- 技能有射程、目标类型、前摇/生效时点、资源消耗和冷却；敌人关键攻击有可读预警、伤害区域和明确结算时点。
- 移动、朝向、距离、地形/遮挡、打断窗口和团队控制都有玩法意义。首发不追求物理模拟；碰撞和技能范围使用简单、可重复测试的形状规则。
- 战斗 HUD 必须显示生命、职业资源、冷却、受控状态、队友危急状态和首领机制；读屏、色弱、减少闪烁和按键反馈纳入首发验收。

### 4.2 战斗规则

- 每名玩家有生命、职业资源、护甲/减伤和状态抗性；攻击由技能定义的伤害类型、攻击属性、目标防御与状态共同决定。基础公式集中在 Combat 模块，不由剧情配置自创算式。
- 首发效果白名单：伤害、治疗、护盾、位移、打断、嘲讽/标记、有限控制、持续伤害/持续治疗和属性增益/减益。首发控制效果设免疫递减或首领抗性，避免无限锁定。
- 首发伤害类型控制在物理与两种元素/能量类型；状态效果先做灼烧、减速、破甲/易伤等少量易读类别。新增类别必须带 UI 图标、叠加/刷新规则、敌我适用范围与反制方式。
- 普攻保证无资源时仍可参与战斗。职业资源由职业定义；不能依赖付费/随机道具维持基本输出。
- 玩家生命归零进入短时倒地，可由队友救援；全队倒地重置当前遭遇或回到最近安全点。首发不永久死亡、不销毁装备；断线重连回到原战斗实例，超时离队按明确的队伍人数规则继续或安全结束。
- 敌人按可声明的状态机行动；行为包含目标选择、移动/攻击意图、冷却/阶段和可配置参数。首领至少有可学习的攻击轮转与阶段变化，不以堆高生命值替代机制。
- 普通敌人/精英/首领职责由行为和组合区分，不以数量和血量无限膨胀制造难度。难度调节优先影响组合、攻击窗口和容错，不隐藏命中或改变已承诺规则。

### 4.3 联机权威与恢复

- 战斗服端为权威：客户端发送带会话、战斗实例、输入序号的意图；服务端验证位置、冷却、资源、目标和命中，客户端不能提交“我造成了多少伤害/掉了什么物品”。
- 同一战斗实例使用单一逻辑权威和固定步进；客户端可预测本地移动并插值他人状态，但伤害、状态、死亡、奖励与任务结果由服务端决定。技术 Spike 必须测量延迟/丢包下的操作手感和权威纠正，再冻结网络频率及插值参数。
- 实时帧/输入不能逐条写 PostgreSQL、Outbox 或事件归档。PostgreSQL 持久化角色、背包、装备、战斗实例检查点、任务/战役结果与奖励账本；Redis 只作在线/瞬时提示，不作奖励或战斗事实的唯一存储。
- 每个遭遇进入/退出及结算边界持久化检查点；恢复时只从最后确认的服务端检查点恢复，并用幂等奖励键避免重复。尚未确认的客户端动画/输入不是已发生的持久事实。
- 需要新增 Combat/Encounter 实例边界和实时消息协议；Query 现有 HTTP 阶段机不是实时战斗权威。WS 不再只是快照刷新提示，但所有实时消息仍逐消息校验会话、成员、序号、速率、大小和战斗权限。

## 5. 角色构筑

### 5.1 属性

首发四项基础属性，升级/装备/效果可改变；属性效果由 Combat/Character 统一计算，任务只引用受限检定：

| 属性 | 主要战斗作用 | 任务作用示例 |
|---|---|---|
| 力量 | 近战伤害、护卫/架势破坏 | 搬动障碍、近身威慑 |
| 灵巧 | 远程/精准攻击、闪避收益 | 追踪、潜入、精细操作 |
| 洞察 | 技能效果、弱点/状态利用 | 发现机关、识别线索关联 |
| 意志 | 生命/抗性、职业资源稳定性 | 抵抗压迫、稳定队友/异常影响 |

属性不得只加抽象战力分。职业有合理基线，装备能偏移构筑；低某属性不能锁死主线关键内容，失败应提供替代路线、代价或战斗后果。

### 5.2 职业与技能

- 首发四个职业原型：守卫（保护/打断）、游击（机动/单体）、术式（范围/状态）、支援（治疗/增益/控制）。它们是战斗倾向，不是队伍门票；任何队伍组合都可通关，任何职业都能造成伤害并自保。
- 每个职业有一个核心资源/机制、基础攻击、闪避和一组职业技能。每次出任务装备四个主动技能；技能定义由不可变内容版本提供，运行时由 Combat 解析，不允许脚本任意改账本。
- 技能按主动/被动/终极能力分类；可解锁等级和技能修饰构成长期成长。修饰应改变可观察的决策（范围、控制方式、资源循环、协同触发等），不只提供小幅数值升级。
- 技能组合与装备词条可形成协同，但同一效果要有上限、触发条件和内部冷却；内容作者不能创建无上限递归触发链。
- 首发提供战斗外免费重配已解锁技能，避免玩家因一次选择被锁出队伍；进战后锁定该次任务构筑，除非任务明确提供安全据点。

### 5.3 成长

- 单角色等级与技能解锁提供可预测成长；职业身份、等级、技能配置、装备和任务关系分别持久化。
- 首发目标为可完整验证的一段有限战役，不建设无限等级或指数装备膨胀。升级不应替代玩家操作；关卡难度按队伍等级/任务区间控制，避免高等级玩家让队友失去参与感。
- 重置/改职业、跨账号角色槽、赛季继承策略以后续产品门禁决定；当前先支持单账号单角色的旧模型，不把它误认为已满足长期 RPG 需求。

## 6. 装备、背包与道具

### 6.1 装备

首发装备位：主手、副手/媒介、头部、身体、手部、足部、遗物；武器决定基础攻击模型，护具和遗物提供构筑方向。所有物品有稳定定义 ID 和实例 ID，实例保存版本、随机结果/词条和来源。

- 品质用于表达词条复杂度/稀有程度，不是唯一强度来源。稀有物有受限数量的词条；传奇级定义少量改变技能或职业机制的独特效果，不能仅靠随机高数值压倒所有选择。
- 随机词条必须来自发布定义的范围、互斥组和预算；服务器生成并保存 seed/最终词条，重试不能重掷。任务奖励以固定奖励池、保底或选择奖励控制结果；首发不让玩家因纯随机长期无法组队。
- 装备比较同时展示主要属性、净变化、技能交互和限制；自动升级提示不能隐去构筑代价。
- 首发不允许玩家交易、拍卖或装备掉落毁损；装备可替换/拆卸，分解/制作仅在经济闭环单独通过评审后加入。

### 6.2 背包与道具

物品分为装备、可堆叠消耗品、任务物品/线索、战役资源。背包与已授权知识是不同边界：已读线索不必占格；剧情线索不能被误卖/丢弃。

- 首发采用有限背包和任务前整理；快捷栏放有限数量消耗品。消耗品效果由服务端验证、记账和冷却；单次任务内和跨任务保留规则显式区分。
- 装备/消耗品获取、使用、装备/卸下和奖励都通过 Player/Inventory 公开命令与账本；命令有预期版本和幂等键，不允许 Query/Combat 直接改背包表。
- 首发可提供治疗、资源恢复、一次性战术工具三类消耗品；限定携带量和补给点，使选择有意义而不是战斗中无限喝药。
- 货币、商店、制作、材料、仓库、玩家交易可扩展，但首发不同时上线多套经济系统。任何材料必须有可理解来源、消耗去处和通胀/囤积上限。

## 7. 任务、战役与内容扩展

任务内容包是不可变、可校验、可回放的发布单位，包含：场景/出口图、交互物、目标状态图、对话/文本 key、遭遇编排、敌人定义引用、奖励表、世界条件和有限后果。内容通过稳定 ID 引用属性检定、技能标签、道具效果和战斗结果，不内嵌 TypeScript 或任意代码。

- 每条主线目标都要有进展路径；属性/技能检定提供额外情报、捷径、优势或代价，不让单次骰值/低属性永久阻断剧情。
- 每个遭遇声明开战条件、敌人组合/出生点、胜利/失败/撤退转移、奖励引用和重试策略；内容验证检查所有状态可达、引用存在、无死循环及奖励边界。
- 世界后果必须映射到后续可见差异，例如下一任务入口、盟友/敌人状态、遭遇单位或对话信息。只改变 Board 数字但无玩家可见影响，不算战役分支完成。
- 对话、线索、任务文本仍走版本化术语/内容系统；战斗日志只公开授权事实。历史实例固定 gameplayReleaseId，热更新不改变在途任务或掉线恢复结果。
- 作者新增一条任务/一个敌人/一个物品时，目标是只提交数据定义和资产，不改核心战斗代码。新机制确需代码时，先扩展白名单效果/行为 schema 并做版本迁移与测试。

## 8. 持久化与模块职责

| 模块 | 权威职责 |
|---|---|
| Identity | 账号、会话、权限；不负责战斗状态 |
| Character/Player | 属性、职业、等级、经验与角色进度 |
| Inventory/Item | 物品实例、背包、装备位、使用/奖励账本 |
| Content/Control | 不可变职业/技能/物品/敌人/任务定义及发布指针 |
| Combat | 实时战斗实例、权威模拟、命中/状态/战斗检查点；不持久化每帧 Outbox |
| Campaign/Mission | 任务实例、目标进度、路线选择、世界后果和奖励计划 |
| World/Board | 可见世界状态与变更账本；Combat 不直接写 Board 表 |
| Social | 大厅/队伍邀请/聊天；不能成为战斗权威 |

跨模块流程按公开命令、持久计划和稳定效果键恢复。一个任务结算计划预先固定经验、物品、世界后果和目标；逐目标确认后完成 Mission，不以“至少一次”投递猜测是否已发奖。活动会话可以高频内存运行，但实例权威、租约/检查点、掉线恢复、崩溃和重复奖励必须先有明确设计，再承载真实玩家进度。

## 9. 首发垂直切片与阶段门禁

垂直切片不是把完整系统缩成永久小玩法，而是用有限内容验证全套系统能否咬合：四个职业各有基础攻击和至少两种主动技能；每职业一条可选构筑分支；六个装备部位至少各有多种定义；包含三类消耗品、三种普通敌人、一种精英和一个有阶段机制的首领；一条约 15–25 分钟任务；战斗中至少一个可由不同构筑处理的目标；完成后有等级/技能或装备选择，并改变一项后续任务可见状态。

执行顺序：

1. **产品与系统冻结**：角色、战斗、掉落、任务/战役闭环与失败/断线规则评审；旧 Query 游戏循环停止扩建。
2. **实时技术 Spike**：浏览器渲染/输入、四人同图、权威移动/命中、延迟/丢包/断线恢复；确认服务器成本与体验，再选固定频率/插值参数。
3. **Combat 纵切**：一张测试场、一种玩家攻击、一种技能、一种敌人与服务端权威伤害；验证命令/帧协议和作弊边界。
4. **角色与物品纵切**：加入四职业基线、技能冷却/资源、背包装备和一个掉落，验证构筑确实改变战斗决策。
5. **战役内容纵切**：加入探索目标、首领、结算/奖励幂等、可见世界后果和数据化任务发布；验证新增内容不需硬编码新状态机。
6. **四人试玩与扩产评估**：观察玩家是否理解操作、协作是否自然、构筑/掉落是否诱发比较和再战意愿、作者是否能稳定产出任务；再决定下一章产能和运营节奏。

验收不以“接口齐全/数值能保存”为成功：新玩家能在无需主持人解释下移动、攻击、使用技能和复活队友；四人网络条件下权威状态一致；每职业有多个有意义构筑；装备/消耗品改变可观察策略；任务失败可恢复/推进；重复结算不重复发奖；第二条任务主要使用内容定义扩展。

## 10. 旧实现的兼容与处置

- 保留可复用的平台能力：身份认证、Player 账号映射、幂等 receipt、PostgreSQL UnitOfWork、Outbox/Inbox、不可变 release、审计、Board 账本及可移植的部署/运维经验；须逐项评估是否适用于高频活动会话。
- 现有 Query 四人创建/加入可作为队伍/房间协调代码的参考，但探索/投票 phase、正确候选裁决、投票奖励和 120/60 秒 UI 不再是新产品主循环。
