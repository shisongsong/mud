# ADR-0001：MVP采用模块化单体

- 状态：Accepted（用户委托下采用设计；独立评审/运行验证未执行）
- 日期：2026-09-30
- 影响：T00、T01、T02及全部模块任务

## 背景

MVP需要身份、试炼、知识、世界、规则、配置和管理多个边界，但团队规模、负载及真实组织边界尚未验证。过早拆服务会引入部署、网络故障和跨服务一致性成本；不设模块边界又会形成共享数据库耦合。

## 决策

玩家API和管理API首期共用server进程；后台任务使用独立worker部署；领域代码按模块封装，只通过公开契约/端口通信。SQL Server表仍按模块所有权管理，不允许跨模块直接读写；本机驱动/隔离级别等兼容性须由T01/T03验证。部署边界以后以负载或组织边界的证据为依据再评估。

## 考虑过的方案

- 微服务：边界尚未实证，首期成本高，暂不采用。
- 无边界单体：开发方便但无法控制内部耦合，不采用。
- 模块化单体：兼顾模块隔离、单仓协作和初期运行简单，作为提案。

## 后果

- 正面：本地业务写事务简单；降低分布式运维成本；可用静态依赖检查执行边界。
- 代价：须严格管理组合根和模块公开API；server/worker需共享契约兼容策略。
- 迁移触发：持续负载/故障隔离/团队独立发布的实证需求达到另行定义的门槛时，提交新ADR。

## 验证与批准

T01须提供禁止依赖环/内部路径导入检查。用户2026-09-30委托助手作设计决策，本方案据此采用；Accepted只表示设计采用，独立文档评审与T01运行证据分别记录，未声称已经通过。
